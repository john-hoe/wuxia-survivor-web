# 05 Development Workflow

## 文档先行流程

任何新功能先写清：

```text
目标：
用户价值：
范围：
非目标：
验收标准：
验证方法：
风险：
```

没有验收标准的功能先不写代码。

## MVP 开发顺序

1. 工程骨架：Phaser + TypeScript + Vite。
2. 空场景：可进入游戏、显示少侠、显示 FPS。
3. P0 视觉基线：少侠、江湖敌人、内力光点、铜钱、剑气/暗器、UI 和基础 VFX 占位资产。
4. P0 声音/HUD/页面基线：主菜单、基础 HUD、暂停页、音量设置、按钮音效。
5. 少侠移动：键盘和触控，并有移动/朝向动画。
6. 江湖敌人追踪：第一种敌人从屏幕外生成并追少侠，并有移动/受击/死亡反馈。
7. 自动招式：第一种招式能自动攻击最近敌人，并有发射/命中 VFX/SFX。
8. 击杀和内力：敌人死亡掉内力光点，少侠拾取后触发领悟，并有吸附动画和拾取音效。
9. 领悟三选一：选择后改变招式或属性，并有领悟反馈。
10. 怪潮节奏：随时间增加江湖敌人数量和种类。
11. 首关头目：第 6 分钟出现 `黑风寨主`，并有攻击预兆动画和预警声音。
12. 阵亡和战后清点：`力竭倒地` 过渡、胜利/失败、铜钱、最好成绩、重开。
13. 局外成长：3 个永久成长项、翻阅秘籍和本地存档。
14. 手感打磨：音效制作、粒子、吸附、受伤反馈、HUD 清晰度、性能。

## 完成定义

一句话原则：

```text
不是“做完就算完”，而是“做完 -> 检查 -> 多模型 review -> 验证 -> 修复 -> 再验收 -> 更新 dashboard”。
```

一个功能完成必须满足：

- 能在浏览器运行。
- 有明确验收标准。
- 没有控制台错误。
- 不破坏已有核心循环。
- 不破坏美术、动画、特效的可读性和性能预算。
- 有简单测试或手动验证步骤。
- 已完成当前有效 review 和必要修复。
- 已按验收标准留下可复查证据。
- 已更新 [26 Task Tracker Dashboard](26-task-tracker-dashboard.md)。
- 如果影响设计，文档同步更新。

## 修复闭环准则

适用范围：

- UI、玩法、视觉、音频、手感、性能和验收失败问题必须完整执行。
- 纯文档或纯配置小改可以轻量执行，但仍要记录原问题、修改点和验证结果。

### 0. 定义问题

如果原始问题不明确：

- 从用户材料中列出可疑问题。
- 给每个问题标注：`确定`、`高概率`、`待确认`。
- 尽量量化判断标准，例如时间、像素、比例、坐标、FPS、事件数。
- 能自行验证的先验证；需要设计拍板的先问用户。

### 1. 问题定位

- 先定位用户指出的原始问题。
- 同时检查同一画面或同一流程里的整体合理性问题，不能只看局部代码是否正确。
- 如果局部验证通过但画面或体验明显不合理，按“问题未解决”处理。

### 2. 制定修复方案

- 修根因，不用 workaround 或 hack 盖住问题。
- 明确本轮修复目标、禁止改动范围、可量化验收标准。
- 如果方案会偏离任务包，必须说明理由；涉及设计取舍时停下来找用户。

### 3. 执行修复

- 只改本轮方案覆盖的文件。
- 不混入无关 WIP，不顺手扩大范围。
- 每次修复后保留可复查证据：截图、视频、日志、测试输出或数值。

### 4. Review 是否真的修复完成

- 不只跑测试，还要从用户视角看最终画面和体验。
- 对原始问题逐条复查：是否真的消失。
- 对整体画面做一次全局检查：是否出现新的显眼问题。
- 每个结论必须有具体证据，例如位置、比例、像素、坐标、截图路径、日志数值。

### 5. 未完成就重来

- 只要发现原问题未消失、新问题明显、验证结果互相矛盾，就回到问题定位。
- 不能把明显问题降级成“后续”来交卷。
- 最多 3 轮仍解决不了，停止并向用户报告根因、已试方案、证据和需要拍板的选择。

## 多模型 review 规则

每个任务进入 `in_review` 前，默认执行：

1. Codex 自审。
2. DeepSeek v4-pro review。
3. local opencode Kimi K2.6 review。
4. Codex 验证、去重、分级所有 finding。
5. 修复真实问题。
6. 重新跑相关检查和必要的窄范围复审。

DeepSeek 已在本机验证可用：`deepseek` 可进入 TUI，`deepseek-tui exec` 可非交互运行，`deepseek models` 显示默认模型为 `deepseek-v4-pro`。为了证据可复查，review 优先使用非交互命令输出到证据目录；TUI 只用于临时人工探索。

如果需要进入 DeepSeek 交互 TUI，启动时使用 `--yolo`，例如：

```bash
deepseek-tui --yolo --workspace <workspace>/VibeGame
```

这样可以避免每次工具调用都要求确认。使用 `--yolo` 时仍必须在 prompt 中明确限定为 read-only review，不能让 DeepSeek 直接编辑文件，除非用户明确授权。

`claude-ds` 从 2026-05-06 起暂时跳过。原因是它在大上下文初审中多次出现代理错误或超时，噪音高于收益。除非用户重新启用或明确要求，本项目后续任务不运行 `claude-ds`，也不把它作为缺失 reviewer 记录。

如果 DeepSeek 或 Kimi 因本地工具、代理或环境失败不可用，必须记录原因，并至少完成 Codex 自审、可运行检查和人工视角复查；不能静默跳过。

## 每轮开发后的检查

证据格式和脚本见 [25 Acceptance Scripts And Evidence](25-acceptance-scripts-and-evidence.md)。

至少检查：

- `npm run build` 通过。
- `npm run typecheck` 通过。
- 开发者自测：桌面浏览器可玩 3 分钟。
- 少侠不会走丢或黑屏。
- 少侠、江湖敌人、内力光点、铜钱、危险范围和领悟反馈能被肉眼分清。
- 命中、击杀、拾取、领悟、受伤至少有一种视觉反馈。
- 命中、击杀、拾取、领悟、受伤、阵亡、按钮至少有基础音效或明确静音设置。
- HUD 不遮挡少侠、江湖敌人、内力光点和危险范围。
- 暂停页能继续游戏，暂停时计时器和伤害停止。
- 主菜单、阵亡过渡、战后清点、翻阅秘籍页面能互相连通。
- 音频素材来源记录不包含 API key 或完整鉴权信息。
- FPS 没有低于目标太多。
- 控制台没有持续报错。

每轮最小证据：

- 本轮完成内容。
- 运行过的命令及结果。
- 至少 1 张关键截图或调试面板截图。
- 若涉及数值，记录对应 metrics。
- 若发现问题，按 P0/P1/P2/P3 分级。

## 最终试玩记录

朋友试玩放在最后：至少等工程骨架、战斗闭环、领悟、怪潮、首关头目、战后清点、铜钱、铜钱抽秘籍、存档、移动端控制和基础手感都完成后再进行。

开发过程中不把朋友试玩作为功能完成条件，只做开发者自测和自动检查。

最终朋友试玩时记录：

| 字段 | 说明 |
| --- | --- |
| player_id | 朋友编号即可，不记录隐私 |
| device | 设备和浏览器 |
| session_seconds | 游玩时长 |
| max_level | 最高等级 |
| kills | 击杀数 |
| result | win / dead / quit |
| first_insight_seconds | 首次领悟时间 |
| wanted_retry | 是否想再来一局 |
| biggest_issue | 最大问题 |

最终试玩最低进入条件：

- `npm run build` 和 `npm run typecheck` 通过。
- 桌面和移动端都能完成至少 1 局或 8 分钟无崩溃运行。
- 核心系统已完成：移动、自动招式、内力领悟、首关头目、战后清点、铜钱、铜钱抽秘籍、存档。
- 已知 P0/P1 为 0。

## 反馈分级

| 等级 | 定义 |
| --- | --- |
| P0 | 崩溃、黑屏、无法移动、无法开始 |
| P1 | 核心循环断裂：打不到怪、升不了级、死因不可读 |
| P2 | 明显影响体验：卡顿、反馈弱、数值太拖 |
| P3 | 打磨项：音效、粒子、文案、局部 UI |

## 禁止把商业化当优化

任何关于“留存、付费、广告、付费抽卡、体力、限时礼包”的建议，都必须先按 `docs/07-no-monetization-policy.md` 判定。默认不进入开发。

铜钱抽秘籍是例外：只要它只消耗游玩铜钱、概率公开、重复补偿、无付费入口、无限时压力，就可以进入局外成长设计。
